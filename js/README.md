# Scripts

There is no build step: the browser loads these files as they are.

- `parts.js`, `splash.js` and `render.js` are plain scripts. `splash.js` sets up the splash shown until the page is ready (`#spl`: the app's picture with its lamps lit in turn), or on the first opening of the day the launch animation (`#spl.launch`: the picture larger, with a soft window over each letter of SANKATAHARA and CHATURTHI, lit later by `features/launch.js`; not for a link to a text, `?add`, a reader who asks for less motion, or a second opening that day: localStorage `sankathara-launch`; a tap or a key ends it, `.skip`), and on any other opening keeps the plain splash about 1.5 s (`#spl.brief`, once a visit: sessionStorage `sankathara-opened`; `features/launch.js` ends it, as in Nitya Upasana) and puts the reader's theme on `<html>` early. `render.js` turns a piece's data into HTML (`renderPiece`, called by `core/page.js` and by `print/compose.js`) and holds the Kannada-letters switch (`SCR`; `SCR.add` puts a piece just built into the chosen script).
- The texts are files (`../content/texts/`). `text/load.js` fetches them as `../content/library.json` lists them (the reading page's sections, each with its texts), with `../content/routines.json` (the evening, into `loaded`), `text/content.js` turns them into the pieces' data (`CONTENT`, read with `text/format.js`), and `core/page.js` builds the pieces into the page with `render.js`. `main.js` waits for the texts before it starts the parts. These three are plain functions with no start-up work of their own; `text/format.js` and `text/content.js` touch no page at all, so the unit tests run them in Node.
- `main.js` is the site script. It is an ES module (`<script type="module">`), and it imports one part per topic from `core/`, `text/` and `features/` (and `store/`, the settings as data).

## How the parts fit together

- Loading a part only defines its functions and variables. Each part's `init()` does its start-up work (reads the page, adds listeners), and `main.js` calls the `init()`s in a fixed order. That is the order the code ran in when it was one file (`app.js`), so a part can rely on everything above it in `main.js` being ready. Each `init()` runs on its own (`run()`): one that throws is reported in the console and the parts after it still start.
- A part imports what it uses from other parts by name, for example `import { P, change } from "../core/state.js"`. Functions can be imported in any order. A variable belongs to the part that sets it, and other parts only read it.
- A value several parts read belongs to the one part that sets it, and the others import it (an imported variable can be read, not changed), as in Nitya Upasana: `FSA` (the default text size for this screen, "100%") and `fontsNow()` in `text/autofit.js`, `rmkPop` (the open dhrupad bubble) in `text/dhrupad-markers.js`, `skCache` (the next Sankathara Chaturthi) in `features/date-card.js`, and `LEAD` (the leading language, set by `apply()` through `setLead()`) in `core/state.js`.
- The settings are `P` (`core/state.js`), saved on this device only (localStorage key `aarti2-prefs`). `apply()` (`features/bars.js`) turns `P` into the `data-*` switches on `<html>` that the styles react to (see `../css/README.md`).
- The layers: `core`, `text` and `store` are the ground (settings, the page, the texts, what is kept); `features` and `print` stand on them. A lower part never imports a feature or the printout: where a feature must know of something a lower part did, the lower part sends a page event and the feature listens (`nitya-fold`: a piece folded, `core/apply.js` → `features/bars.js`). `tests/site-files.spec.mjs` checks this.
- A new file must also be added to `parts.js`, so it is kept for offline use. `tests/site-files.spec.mjs` checks this.
